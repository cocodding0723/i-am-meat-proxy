# 커밋 전 사용자 검수

## 검수 자료

1. 현재 저장소·브랜치·upstream·Git 상태와 적용 지침을 확인한다. 기존 사용자 변경과 이번 작업 파일을 구분한다. 검수 목적으로 먼저 stage하지 않는다.
2. 구현, 관련 테스트, diff 정리를 끝낸다. 실행한 검증과 미실행 검증을 분리한다. 무관한 전체 테스트 반복은 피한다.
3. 사용자에게 변경 목적, 주요 전후 동작, 정확한 파일 목록, 테스트 결과, 남은 위험을 짧게 보여준다. 필요하면 파일 링크·diff를 덧붙인다.
4. 이번 변경 범위에 대한 사용자 검수·커밋·push 승인이 있는지 확인한다. 승인 없으면 구체적인 결과를 보여준 뒤 응답을 기다린다. 시간 경과, 테스트 통과, 에이전트 자체 검토는 사용자 승인이 아니다.
5. 승인이 확인된 범위만 stage하고 staged diff를 재확인한다. 관련 없는 staged 파일이 있으면 그대로 보존하고 커밋 범위를 분리한다. `git add -A`, 자동 stash·reset·rebase·강제 push를 쓰지 않는다.

## 승인 범위

- 사용자가 이번 작업의 커밋·push·업로드를 이미 명시적으로 요청했다면 그 승인을 재사용한다. 구현 요청만으로 게시 승인을 추정하지 않는다.
- 승인 후 의미 있는 변경이 추가되면 변경분을 다시 제시한다. AI가 승인 상태나 사용자의 발언을 만들어내지 않는다.
- 검수 UI는 선택 사항이다. GitHuman 설치나 브라우저가 없어도 대화에서 파일·diff를 보여주고 승인받을 수 있다.
- 승인 뒤 간결한 한국어 커밋 메시지를 사용한다. 사용자가 요청한 경우 `git push -u origin HEAD`를 실행하고 `git ls-remote`로 원격 SHA를 비교한다.
- commit과 push를 별도로 보고한다. push 실패 시 로컬 커밋 SHA와 실패 원인을 남기며 완료라고 하지 않는다.

검수 요청 예시: “변경 3개 파일, 로그인 회귀 테스트 8개 통과. 미확인: 실기기 로그인. 이 변경을 커밋·push해도 될까요?” 실제 확인값으로만 작성한다.
