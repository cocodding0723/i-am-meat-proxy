# QA 체크리스트

목표: **QA가 이 한 장만 보고 준비부터 판정까지 끝낸다.** 다른 문서 링크, 케이스 ID, 앵커는 넣지 않는다.

## 진행

1. 변경 범위 파악. `git log --oneline <base>..HEAD`와 `git diff --stat`로 바뀐 기능을 찾는다. base는 사용자가 말한 브랜치, 없으면 `develop` 또는 `main`.
2. 화면에서 보이는 효과만 고른다. 코드로만 확인되는 동작(저장, 로그, 내부 상태)은 "화면으로 확인 불가"라고 한 줄 적고 항목에서 뺀다.
3. 기대 결과는 코드에서 근거를 찾아 쓴다. 근거가 없으면 "확인 필요"로 표시하고 6장에 모은다.
4. 아래 구조로 `docs/qa/<기능명>.md` 한 파일에 쓴다. 사용자가 경로를 말했으면 그 경로.
5. `eval.md`의 점검 항목을 하나씩 통과/실패로 판단한다. 실패가 있으면 고치고 다시 점검한다.
6. 사용자에게 "확인 필요" 목록만 보여 준다. 문서 본문을 다시 설명하지 않는다.

## 두 가지 요청

- **작성** (기본): 위 순서대로 문서를 만든다.
- **점검**: 사용자가 기존 QA 문서를 주고 "점검해", "뭐가 문제야"라고 하면 다시 쓰지 않는다. `eval.md` 항목 중 실패한 것만 문서의 해당 줄을 인용해 짧게 알려 준다. 고칠지는 그 뒤에 묻는다.

## 문서 구조

```
# <기능> QA 체크리스트

이번에 바뀐 것: <1~2줄. 사용자 입장에서 무엇이 달라졌는지>

## 준비
- [ ] <빌드/앱 종류>
- [ ] <계정·기기·데이터>

## 하는 법
| 이름 | 방법 |            ← 문서에 나오는 화면·조작만. 3~8줄
| 화면 이름 | 실제 글자 |   ← 판정에 쓰는 문구가 있을 때만

## 확인
### <그룹>
- [ ] **항목 이름** — 준비. 할 일 → 할 일. → 이렇게 나와야 함.
...

## 실패하면
항목 이름 · 사진 · (서버 설정이면) 게시 버전을 적는다.

## 확인 필요
- <담당자가 정해야 답이 나오는 것>
```

## 항목 쓰는 규칙

- 한 항목 = 한 줄. `준비 → 할 일 → 나와야 하는 것` 순서. 화살표 `→`로 단계 구분.
- 이름은 동작 중심으로 짧게 (`열린 창이 바로 바뀜`, `설정 삭제`). `A01`, `TC-` 같은 ID 금지.
- 서버 값, 앱이 실제로 쓰는 값, 화면 결과를 구분한다. 서버 저장 성공만으로 앱 반영을 판정하지 않는다.
- 토글은 두 값의 의미를 모두 적는다 (`false: 점검 중 / true: 정상`). ON/OFF만 쓰지 않는다.
- 정상 경로 → 잘못된 입력 → 삭제·누락 → 오프라인·재시작 → 기존 기능 회귀 순으로 그룹을 둔다. 해당 없는 그룹은 뺀다.
- 항목 수는 한 화면에 들어오게. 40개가 넘으면 그룹을 나누라고 사용자에게 묻는다.
- 이식 검사: 항목을 다른 앱에 그대로 옮겨도 말이 되면 구체성이 부족한 것이다. 이 앱의 화면·설정 이름·값을 넣는다.
- 계정, 빌드 종류는 QA가 정하지 않는다. 빈칸으로 두고 "담당자가 채움"을 붙인다.
- 시간은 초 단위로 적지 않는다. "잠시 기다린 뒤에도 안 바뀌면 실패" 정도로 쓴다. 캐시 때문에 오래 걸리는 경우만 "5분 뒤 다시 확인"처럼 따로 적는다.
- 존재하지 않는 테스트 버튼·디버그 화면을 준비 완료처럼 쓰지 않는다.

## 문장

- "~합니다"체. 짧은 문장. 전문 용어는 처음 나올 때 한 줄로 뜻을 적는다.
- 슬래시·괄호 중첩 금지. 비교는 표, 순서는 번호, 이유는 문장.
- `기본적으로`, `~하게 됩니다`, `~할 수 있습니다` 같은 필러 제거.
