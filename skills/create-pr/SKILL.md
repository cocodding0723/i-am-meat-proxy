# PR 작성·등록

1. 원격 저장소, 현재 브랜치, 실제 기본 브랜치, 기존 PR을 확인한다. `main`을 고정 가정하지 않는다. `gh` 또는 연결된 GitHub 도구를 사용한다.
2. 저장소 PR 템플릿·기여 규칙, 기준 브랜치부터의 커밋·diff, 연관 Issue를 읽는다. 마지막 커밋만 보고 전체 변경을 요약하지 않는다.
3. 문제와 결과 동작을 먼저 설명한다. 주요 변경, 실제 검증, 미확인 사항, 관련 Issue를 필요한 만큼 채운다. 검증하지 않은 체크박스는 체크하지 않는다. 일부만 해결하면 `Related to #N`, 완료되는 Issue에만 `Closes #N`을 쓴다.
4. 커밋되지 않은 변경이 있으면 설치된 `review-before-commit` 스킬로 검수·승인 범위를 확인한다. PR 준비를 이유로 자동 stash·rebase·reset·squash·강제 push하지 않는다.
5. 초안 작성 요청이면 본문을 보여주고 끝낸다. 등록 요청이 이미 명시됐다면 권한을 재질문하지 않고 생성한다. 범위가 달라지거나 게시 승인이 없으면 완성된 초안을 먼저 보여준다. 리뷰어 호출·댓글·merge는 해당 지시가 있을 때만 수행한다.

## 등록

멀티라인 본문은 임시 파일로 작성해 `gh pr create --title '제목' --body-file /절대경로/pr.md --base 실제기준브랜치 --head 현재브랜치`에 전달한다. 작업 미완료나 사용자 요청 시 `--draft` 사용. shell 문자열에 본문을 직접 끼워 넣지 않는다.

이미 같은 브랜치 PR이 있으면 중복 생성하지 않는다. 수정 요청 범위만 `gh pr edit --body-file`로 갱신한다. 생성 결과가 불명확하면 먼저 PR 목록을 조회하고 무조건 재시도하지 않는다.

최종 확인: PR URL, base/head, 제목·본문, draft 상태를 다시 읽는다. CI 실행 예정과 실제 통과를 구분해 보고한다. PR 등록 성공은 merge 성공이 아니다.
